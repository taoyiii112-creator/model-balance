# 多端数据同步方案设计（桌面 / 网页 / 手机）

> 状态：方案设计（待用户确认后实施）。作者：Codex，2026-08-08。

## 目标

桌面端、网页版、手机端共享同一份数据：余额快照（趋势）、Token 用量记录、账户元数据（不含 API Key）。
现状：三端各自本地 SQLite，数据不互通。

## 核心原则

- **API Key 永不上传**：密钥只存在各端本地（桌面 .env / 手机 Keystore），服务端只存账户元数据与使用数据。
- **离线可用**：各端本地 SQLite 保留为离线缓存；联网时同步。
- **兼容现有表结构**：复用 usage_records / balance_snapshots 的结构，减少改造。

## 方案 A：中心化后端（推荐）

```
各端（桌面 / 网页 / 手机）──► 后端 API（REST/JSON）──► 数据库（MySQL 或 SQLite）
```

1. **后端**：Python 轻量服务。
   - 选项 1（推荐，贴合项目零依赖风格）：纯标准库 `http.server` 实现 REST API，部署简单。
   - 选项 2：FastAPI + uvicorn（需装依赖，功能强、文档自动生成）。
2. **存储**：
   - 初期：SQLite（单文件，部署零成本）。
   - 上规模 / 多用户：本机 MySQL（遵循全局数据库规则：读 codex_ro / 写 codex_rw、写操作确认 + 备份 + 审计）。
3. **API 设计**（前缀 /api/v1，JSON）：
   - `POST /api/v1/sync/usage`（批量上传用量记录，按 created_at 去重）
   - `GET /api/v1/sync/usage?since=<ts>`（增量拉取用量）
   - `POST /api/v1/sync/snapshots` / `GET /api/v1/sync/snapshots?since=<ts>`（余额快照）
   - `GET /api/v1/accounts`（账户元数据：名称/提供商/币种，**不含 Key**）
   - `GET /api/v1/health`
4. **认证**：每端一个设备令牌（简单 token，配置在端上，不登录系统）；可选后续加用户体系。
5. **冲突策略**：按 `created_at` + 端优先级（服务端为准）；同一记录以 id 去重。
6. **各端改造**：
   - 桌面：新增 `sync.py`（定时/手动同步），storage 读写走本地 + 同步层上传/拉取。
   - 网页：web 后端加同步端点，或直接连同一后端。
   - 手机：`storage_service.dart` 加同步方法，设置页加"同步"开关与服务器地址。

## 方案 B：手动导出 / 导入（最低成本，不推荐长期）

- 桌面 `export` / `import` 命令导出 JSON，手机/网页手动导入。
- 优点：无需后端。缺点：非实时、易冲突。仅作过渡。

## 实施阶段

- P1：后端 API + 数据库建表 + health/sync 端点（桌面仓库内新增 `server/` 子目录）。
- P2：桌面端接入同步（设置里配置服务器地址 + 令牌，定时同步 + 手动按钮）。
- P3：手机端接入同步。
- P4：网页版接入（可选）。
- 每阶段独立验证（pytest / flutter test），通过后发布（发布需授权）。
